# DMX 项目工程化管理策略

版本：1.0
日期：2026-09-04
适用范围：`DMX` 正式程序、`DMX_test` 回放程序、目标检测模型、数据集、设备接入脚本及配套文档

## 1. 目标

本策略的目标不是增加审批层级，而是让 DMX 项目具备以下能力：

1. 任意一次发布都能找到对应的源码、配置、模型和测试数据。
2. 每项需求有负责人、验收条件、测试记录和变更历史。
3. 算法改进能够用固定基准量化，不依赖主观观察。
4. 正式设备出现问题时，可以快速定位、收集证据和回滚。
5. 新成员可以按模块接手，不需要先理解整个项目。
6. 数据、模型、程序和设备配置分别管理，避免相互覆盖。

核心原则：

- `main` 分支始终保持可构建、可测试、可发布。
- 小批量、短周期、可回滚地更新，避免长期积累成一次大改。
- 测试结论必须绑定 Git 提交、配置、模型和数据集版本。
- 线上事实以结构化运行日志为准，口头描述只作为补充。
- 原始数据只读保存，派生数据可以重建。
- 实时性、误报率和稳定性与识别精度同等重要。

## 2. 当前现状与首要风险

截至 2026-09-04，仓库已有较好的技术基础：

- Git 已连接远程仓库，`main` 与 `origin/main` 当前指向 `83b3f3b`。
- 已有 41 个提交，提交信息基本采用 `feat/fix/perf/docs` 风格。
- 已有 Qt 单元测试、Python 测试、本地回放程序和真机启动脚本。
- 已有按日期保存的应用日志、UDP 原始日志、候选图 manifest 和天空 Mask 归档。
- `DMX_test` 与 `DMX` 共用主要源代码，适合建立统一回归测试。

目前最大的工程风险不是缺少功能，而是缺少“可信版本边界”：

- 工作区存在约 21 个已修改项、53 个未跟踪项和 2 个删除项。
- 很多已经在使用的核心文件仍未进入 Git，例如 `DMX_test.pro`、`directyolomanager.*`、`radar_ui/` 和多项工具。
- `build_linux_test/`、`build_panoramacache_tests/` 等构建目录未全部纳入忽略规则。
- `TASK_HANDOFF.md` 中部分算法、模型和配置说明已落后于当前实现。
- 正式运行、快速回放和冷启动 Mask 回放依赖大量环境变量，配置差异不够显式。
- 算法评估脚本较多，但还没有统一入口、统一报告格式和统一质量门槛。

因此第一阶段必须先建立一个可复现基线，再开始多人并行开发。

## 3. 项目治理与角色

团队规模较小时，一个人可以兼任多个角色，但职责必须明确。

| 角色 | 主要职责 | 不能省略的输出 |
|---|---|---|
| 项目负责人 | 需求优先级、里程碑、风险和最终验收 | 迭代计划、发布批准 |
| 架构/主程 | 模块边界、公共接口、并发和性能设计 | 设计说明、关键代码评审 |
| 算法负责人 | 数据、模型、阈值、融合策略和指标 | 模型卡、评估报告 |
| 设备与运维负责人 | 网络、挂载、端口、转台、部署和故障处理 | 部署记录、巡检和故障报告 |
| 测试负责人 | 测试用例、回归执行、缺陷复现和验收 | 测试报告、发布结论 |
| 模块维护人 | 对指定目录的代码质量和文档负责 | Review、模块说明 |

最低评审原则：

- 作者不能只凭“本机运行正常”自行宣布正式发布。
- 普通修改至少经过一次代码审查或独立复测。
- 算法、协议、线程、存储和转台控制修改必须由对应模块维护人确认。
- 真机发布至少由开发和测试/设备人员分别确认一次。

后续可使用 `.github/CODEOWNERS` 固化目录负责人。

### 4.2 大文件拆分原则

当前 `videothread.cpp` 和 `mainwindow.cpp` 已承担过多职责。不要一次性重写，应采用“先测试、后提取、行为不变”的方式逐步拆分：

1. 先为准备拆出的行为补测试或回放断言。
2. 定义输入输出结构，避免模块之间传递大量散乱参数。
3. 每次只抽取一个职责并单独提交。
4. 拆分提交不得同时调整算法阈值或界面行为。
5. 拆分前后使用同一基准数据，指标必须一致。

建议优先从 `videothread.cpp` 提取：

- `PathReceiver`：UDP 路径接收和原始日志。
- `FrameDecoder`：文件等待、解码、旋转和镜像。
- `SkyMaskBuilder`：前三圈采样、后台建模和归档。
- `TraditionalDetector`：背景差、BlackHat、形态分析和候选评分。
- `DetectionCoordinator`：检测门控、队列和候选汇总。

建议从 `mainwindow.cpp` 提取：

- `RuntimeController`：设备启动、停止和运行状态。
- `DetectionPresenter`：候选转换为 `TargetRecord`。
- `ReplayController`：测试模式和模拟角度。

## 5. 任务管理流程

### 5.1 任务类型

统一使用以下前缀：

- `EPIC`：跨模块的大目标。
- `FEAT`：新增能力。
- `BUG`：明确错误。
- `PERF`：实时性、内存、GPU或队列优化。
- `ALG`：检测、融合、阈值或模型改进。
- `DATA`：采集、标注、清洗和数据集版本。
- `MODEL`：训练、转换、模型发布和回滚。
- `OPS`：部署、挂载、监控和日志。
- `DOC`：说明书、设计、交接和专利材料。
- `REFACTOR`：行为保持不变的结构整理。

### 5.2 状态流转

```text
Backlog -> Ready -> In Progress -> Review -> Verify -> Done -> Released
```

- `Backlog`：只有想法，信息可能不完整。
- `Ready`：范围、验收条件、数据和负责人已经明确。
- `In Progress`：正在开发，每人同时最多 1～2 项。
- `Review`：代码已完成，等待审查。
- `Verify`：在规定环境执行测试或真机验证。
- `Done`：代码和测试完成，但不一定已正式发布。
- `Released`：已进入带版本号的正式发布包。

### 5.3 每个任务必须包含

```text
标题：BUG-目标靠近0度时候选图出现横向黑边
背景：问题发生在哪个版本、模式和数据上
范围：修改哪些模块，不修改哪些行为
复现：输入、步骤、日志、截图或样本编号
验收：可以客观判断通过/失败的条件
风险：实时性、兼容性、数据和设备风险
测试：单测、回放、真机分别需要什么
负责人：开发、评审、测试
```

任务禁止使用“优化一下”“处理一下”作为唯一验收条件。

## 6. Git 管理策略

### 6.1 分支模型

采用轻量级主干开发，不长期维护多个开发分支：

- `main`：始终可构建、可回放、可发布。
- `feature/<issue>-<name>`：功能开发。
- `fix/<issue>-<name>`：缺陷修复。
- `perf/<issue>-<name>`：性能优化。
- `alg/<issue>-<name>`：算法修改。
- `ops/<issue>-<name>`：运维和部署。
- `docs/<issue>-<name>`：文档。
- `release/<version>`：只在发布冻结期短暂存在。
- `hotfix/<issue>-<name>`：正式版本紧急修复。

示例：

```bash
git switch main
git pull --ff-only
git switch -c fix/DMX-142-panorama-crop-wrap
```

分支应尽量在 1～3 天内合并。超过一周的任务应继续拆分。

### 6.2 提交规范

使用 Conventional Commits 风格：

```text
feat(radar): add target class label
fix(pano): wrap candidate crop across 360 seam
perf(mask): move mask archive to background worker
test(replay): assert no inference before mask readiness
ops(startup): verify model and mount before launch
docs(manual): update live capture procedure
```

要求：

- 一个提交只解决一个逻辑问题。
- 功能代码和对应测试放在同一提交或连续提交中。
- 不提交构建产物、日志、原始数据、虚拟环境和临时截图。
- 不在提交中包含密码、私钥、共享盘凭据或设备敏感信息。
- 不使用 `git add -A` 盲目提交当前整个工作区。
- 提交前执行 `git diff --check` 和对应测试。

### 6.3 Pull Request 门禁

每个 PR 至少包含：

- 关联 Issue。
- 修改原因和行为变化。
- 风险和回滚方法。
- 测试命令与结果。
- 算法修改的前后指标。
- UI 修改的前后截图。
- 配置、端口、路径和模型是否变化。

合并条件：

- 自动测试通过。
- 无未解释的新增编译警告。
- 至少一名评审人批准。
- 算法和性能指标达到任务验收标准。
- 文档和配置说明同步完成。

禁止直接向 `main` 强制推送。远程仓库应开启分支保护和 PR 合并要求。

### 6.4 当前脏工作区的基线处理

这是首要任务，建议单独安排，不与新功能混做：

1. 对当前目录和重要外部配置做一次只读备份。
2. 导出当前 `git status`、`git diff` 和未跟踪文件清单。
3. 人工确认两个删除文件是否应删除，不自动恢复或确认删除。
4. 补充 `.gitignore`，至少覆盖 `build_linux_test/`、`build_*_tests/` 和临时分析目录。
5. 将未跟踪项分为源码、测试、文档、运行脚本、临时文件、数据六类。
6. 在 `integration/engineering-baseline-20260904` 分支整理。
7. 依次执行配置测试、缓存测试、负样本测试、Python测试、两个主程序编译和固定回放。
8. 生成一份基线验证报告。
9. 当前积累内容无法完全拆分历史时，允许做一次明确标记的基线提交。
10. 给基线打附注标签，例如 `baseline-2026.09.04`，以后恢复以该标签为准。

基线建立后，要求日常工作结束时 `git status` 可解释；准备发布时必须为空。

## 7. 版本、变更记录与可追溯性

### 7.1 四类版本必须分开

| 对象 | 示例 | 管理方式 |
|---|---|---|
| 应用版本 | `v0.9.0` | Git Tag + 发布包 |
| 配置版本 | `config-20260904.1` | Git 文件 + SHA256 |
| 模型版本 | `detector-weights5-r1` | 外部模型仓库 + manifest + SHA256 |
| 数据集版本 | `baseline-20260723-v1` | 只读目录 + manifest + SHA256 |

不得只写“最新模型”“最终版”“最终改版”。正式发布必须使用不可变版本号和校验值。

### 7.2 应用版本规则

在产品正式稳定前可使用：

```text
v0.<功能迭代>.<修复号>
```

进入稳定发布后使用语义化版本：

- 主版本：不兼容协议或架构变化。
- 次版本：兼容的新功能。
- 修订版本：兼容的问题修复。

测试版使用 `-rc.1`，例如 `v1.2.0-rc.1`。

### 7.3 三层变更记录

1. Git Commit：开发级事实，一次小变更一条。
2. PR/Issue：说明为什么改、怎么测、风险是什么。
3. `CHANGELOG.md`：只记录用户可感知变化、兼容性和升级注意事项。

重大技术决策另写 ADR：

```text
docs/adr/0001-direct-yolo-full-frame.md
docs/adr/0002-three-panorama-mask-gate.md
```

ADR 包含背景、方案、取舍、后果和替代方案。不要把所有历史都继续堆入 `TASK_HANDOFF.md`。

### 7.4 每次运行的身份信息

程序启动日志和 `run_manifest.json` 应写入：

```json
{
  "runId": "20260904_101530_hostA",
  "appVersion": "v0.9.0-rc.1",
  "gitCommit": "abcdef1",
  "gitDirty": false,
  "buildTime": "2026-09-04T10:00:00+08:00",
  "configSha256": "...",
  "modelId": "detector-weights5-r1",
  "modelSha256": "...",
  "datasetId": "live-or-baseline-20260723-v1",
  "mode": "live",
  "host": "dmx-host-01"
}
```

正式发布禁止使用 `gitDirty=true` 的二进制。

## 8. 配置与运行模式管理

当前大量环境变量散布在启动脚本中，建议形成显式配置档案：

```text
config/base.json
config/live.json
config/replay-fast.json
config/replay-cold-mask.json
config/replay-performance.json
```

- `live`：真实共享盘、真实端口、前三圈建模。
- `replay-fast`：允许预加载固定 Mask，用于快速算法回归。
- `replay-cold-mask`：禁止预加载 Mask，用于验证前三圈和后台建模。
- `replay-performance`：固定输入速率，输出完整性能统计。

启动脚本只选择 profile 和覆盖机器相关路径，不再重复维护全部算法参数。

配置修改要求：

- 每个配置项有类型、单位、范围、默认值和说明。
- 启动时打印最终生效值，而不是只打印配置文件值。
- 未识别配置项应报警，关键项缺失应拒绝启动。
- 正式发布把配置副本写入运行目录。
- 阈值修改按算法变更处理，必须有评估报告。

## 9. 测试体系

### 9.1 四级测试

#### A. 单元测试

目标：秒级完成，定位到函数或类。

当前基础：

- `appconfig_tests`：配置解析和环境覆盖。
- `panoramacache_tests`：全景分块、并发和360度裁剪。
- `manualnegativestore_tests`：负样本保存和反馈。
- `tests/test_*.py`：回放、拼接和数据工具。

后续重点补充：

- 天空 Mask 完整三圈判定。
- 传统候选评分和 NMS。
- RGB/BW 同目标融合。
- 目标过期和列表去重。
- 高度角换算。
- YOLO 输出格式解析。
- 队列丢帧阀门。

#### B. 集成回放测试

目标：验证模块串联，但不依赖真实设备。

固定使用 `baseline-20260723-v1`，至少包含：

- 快速 Mask 模式：检查识别结果和界面事件。
- 冷启动 Mask 模式：检查前三圈不推理、后台建模和归档。
- 性能模式：按 8 秒/圈、16 个分块、RGB/BW 配对回放。
- 故障模式：缺图、乱序、延迟、路径不存在、共享盘中断。

每次回放自动生成 `summary.json`，不得依靠人工翻完整日志得出结论。

#### C. 系统与界面测试

目标：验证实际可用流程。

- 一键启动、关闭和重复启动锁。
- 主界面、ROI、极坐标雷达、目标列表和预览联动。
- 1920×1080、常用窗口尺寸和高 DPI 截图检查。
- 目标靠近全景左右边界时无横向黑边。
- 目标位于上下边界时垂直补黑正确。
- 长时间运行时界面无持续卡顿和内存增长。

#### D. 真机验收

目标：验证实验室环境无法模拟的设备行为。

- 网线、路由、SMB共享、RGB/BW文件可读。
- UDP 5001/5002/8001 等端口按协议工作。
- 转台启动、停止、8秒/圈和异常停止。
- 三圈 Mask 建模期间不输出检测目标。
- 真实采集至少连续运行 30 分钟。
- 断网、共享盘卸载、模型进程退出和磁盘不足时有明确告警。

### 9.2 一键测试入口

最终应提供统一脚本：

```bash
./scripts/test_fast.sh          # 单测、JSON、Python测试
./scripts/test_build.sh         # DMX和DMX_test编译
./scripts/test_replay_smoke.sh  # 1～2分钟快速回放
./scripts/test_replay_full.sh   # 完整基准评估
./scripts/test_hil_checklist.sh # 真机检查记录
```

所有脚本失败时返回非零状态码，便于 CI 判断。

### 9.3 初始质量门禁

以下是建议的第一版门槛，建立基线后再根据实测调整：

| 类别 | 建议门槛 |
|---|---|
| 构建 | `DMX`、`DMX_test` 均成功，无新增未解释警告 |
| 单测 | 100%通过 |
| 配置 | JSON合法，关键路径和参数可追溯 |
| Mask门控 | 冷启动前三个完整全景无任何图像推理和目标输出 |
| Mask线程 | 建模/归档期间路径队列不持续增长 |
| 回放吞吐 | 8秒/圈基准下连续30分钟不形成累积积压 |
| 路径队列 | 稳态不超过配置上限，发生丢帧必须计数 |
| 推理时延 | 单帧端到端 p95 小于一个同流帧周期，当前基准建议先设为500ms |
| UI | 主显示目标25 FPS以上，操作无秒级冻结 |
| 稳定性 | 30分钟无崩溃、无失控内存增长、无残留子进程 |
| 数据完整性 | 原始UDP日志可解析，run manifest和summary完整 |

## 10. 算法与模型评估

### 10.1 数据集划分

必须按日期、地点或采集场景划分训练/验证/测试集，不能把同一目标连续帧随机拆到不同集合。

建议维护：

- `train`：允许持续加入人工负样本。
- `validation`：用于选阈值和训练停止。
- `test-fixed`：冻结，只用于版本比较。
- `field-test`：每次真机采集后独立统计。

`20260723` 回放数据作为系统性能和回归基准，不等于完整的算法泛化测试集。

### 10.2 三层指标

#### 模型层

- Precision、Recall、F1。
- mAP@0.5、mAP@0.5:0.95。
- 各类别混淆矩阵：无人机、飞鸟、民航飞机、背景。
- 不同目标尺寸、距离、RGB/BW场景分组指标。

#### 事件层

- 每个真实目标是否至少命中一次。
- 首次发现延迟。
- 同一目标重复事件数量。
- RGB/BW合并正确率。
- 目标分类准确率。
- 固定结构和树叶造成的误报次数。

#### 系统层

- 每小时误报数 `false alarms/hour`。
- 每圈漏检率。
- 图像接收、解码、Mask、YOLO、融合、UI各阶段 p50/p95/p99。
- 最大队列、丢帧数、CPU、内存、GPU利用率和显存。
- Mask建模耗时、检测开始圈次和归档耗时。

### 10.3 算法变更报告

每次更换模型、阈值或融合规则必须生成：

```text
reports/evaluation/<version>/
  report.md
  metrics.json
  confusion_matrix.png
  pr_curve.png
  latency.csv
  false_positives/
  false_negatives/
  run_manifest.json
```

报告至少对比“当前正式版本”和“候选版本”。推荐初始回归规则：

- 固定测试集 Recall 不下降超过 2 个百分点。
- 每小时误报不增加超过 10%。
- p95 延迟不得超过实时门槛。
- 如有指标退化，必须写明业务收益并由负责人批准。

## 11. 数据与模型治理

### 11.1 数据不直接进入 Git

Git 只保存代码、配置、标签和小型 manifest。以下内容放在数据盘或对象存储：

- 原始 RGB/BW 图像。
- UDP 原始日志。
- 候选截图和负样本。
- 训练集、训练输出和模型权重。
- 大型 PDF、视频和性能原始文件。

每个数据集在 Git 中保存一个小型版本描述，例如：

```text
datasets/baseline-20260723-v1.json
models/detector-weights5-r1.json
```

内容包括绝对/逻辑位置、文件数、时间范围、采集设备、生成脚本提交、SHA256和负责人。

### 11.2 数据生命周期

```text
raw/ -> curated/ -> labeled/ -> split/ -> evaluation/
```

- `raw`：原始数据，只读，不覆盖。
- `curated`：去除损坏和无效样本，保留来源引用。
- `labeled`：标注和复核结果。
- `split`：冻结的训练/验证/测试清单。
- `evaluation`：版本评估输出，可按规则清理后重建。

人工标记误检进入负样本池后，必须有 `待复核/已确认/已入训/已废弃` 状态，防止误把真实目标加入负样本。

### 11.3 模型发布

模型发布不能只复制 `best.onnx`。每个模型版本应包含：

- 模型 ID 和 SHA256。
- 训练代码 Git 提交。
- 数据集和划分版本。
- 类别顺序。
- 输入尺寸、归一化和后处理参数。
- 训练曲线和验证指标。
- ONNX Runtime/CUDA 兼容信息。
- 已知限制和推荐阈值。

正式启动脚本引用固定模型 ID；`latest` 只能供研发使用。

## 12. 日志、监控与运维

### 12.1 日志分层

建议每次运行创建独立目录：

```text
/mnt/dmx4t/data/runs/YYYYMMDD/<run_id>/
  run_manifest.json
  app.log
  metrics.jsonl
  events.jsonl
  config_effective.json
  environment.txt
  summary.json
```

- `app.log`：供人阅读的状态和错误。
- `metrics.jsonl`：队列、耗时、帧率、内存和GPU指标。
- `events.jsonl`：检测、融合、删除和人工反馈事件。
- `summary.json`：程序退出时或运维工具生成的摘要。
- 原始 UDP 日志继续独立保存，不能混入普通应用日志。

### 12.2 必须监控的运行指标

- 共享盘和数据盘是否挂载。
- 剩余磁盘空间及写入失败。
- RGB/BW最近一帧时间和接收速率。
- 路径队列、丢帧和解码失败。
- 全景有效分块数和当前圈次。
- Mask状态：收集、建模、就绪、失败。
- YOLO进程状态、队列延迟、推理耗时和重启次数。
- 候选数、融合数、误检人工标记数。
- UI刷新率、进程CPU/内存、GPU利用率和显存。
- 转台状态和指令应答。

### 12.3 运维工具

建议建立：

```text
ops/dmx-doctor.sh              # 启动前诊断
ops/dmx-status.sh              # 当前进程和设备状态
ops/dmx-collect-support.sh     # 收集脱敏故障包
ops/dmx-log-summary.py         # 生成一次运行摘要
ops/dmx-disk-audit.sh          # 数据目录容量与保留期检查
```

`dmx-doctor` 至少检查：

- 网卡 carrier、IP和设备连通性。
- `/mnt/dmx_share`、`/mnt/dmx4t`。
- 关键端口占用。
- 配置文件、模型、Python环境和CUDA Provider。
- 数据目录可写和剩余空间。
- 上一次异常退出的锁文件或残留进程。

### 12.4 日志和数据保留

在自动删除前必须先批准保留策略。建议：

- 发布与故障运行日志：长期保留。
- 普通运行文本日志：保留 90 天。
- 性能 metrics：保留 180 天或压缩归档。
- 原始基准数据：永久只读保留，并至少有第二份副本。
- 普通候选图：按项目需求保留 90～180 天。
- 已确认负样本和标注数据：纳入数据集版本后长期保留。
- 可重建的缓存和临时分析目录：定期清理。

清理脚本必须支持 `--dry-run`，默认只报告、不删除。

## 13. CI、夜间任务与真机流水线

### 13.1 每次 PR 的快速 CI

可使用 GitHub Actions 或内网 Runner：

1. 检查 JSON、脚本语法和 Git 空白错误。
2. 执行 Python 单元测试。
3. 编译并运行 Qt 单元测试。
4. 编译 `DMX` 和 `DMX_test`。
5. 保存测试结果和编译日志。

CI 不需要访问真实共享盘、4T盘或GPU模型。

### 13.2 GPU 工作站夜间任务

- 完整回放基准。
- 冷启动 Mask 回归。
- 30分钟稳定性测试。
- 候选和事件级指标。
- 性能趋势对比。
- 失败时保留日志、配置和关键截图。

### 13.3 真机发布门禁

真机流水线不能完全由云端 CI 替代。发布前执行签字式电子清单：

- 设备网络和共享盘。
- 相机与转台。
- 正式模型和配置校验值。
- 三圈建模和检测门控。
- 识别、雷达显示、人工负样本。
- 30分钟稳定运行。
- 停止、重启和回滚。

### 14.1 发布流程

- 应用二进制。
- 配置。
- 模型引用。

正常回滚通过切换 `current` 到上一已验证版本完成，不在现场临时重新编译。

## 15. 故障与缺陷管理

### 15.1 严重级别

- `P0`：设备失控、数据破坏、安全风险，立即停止运行。
- `P1`：主程序无法启动、持续漏帧、检测完全不可用，优先修复。
- `P2`：部分功能错误、明显误报或性能退化，进入当前迭代。
- `P3`：界面细节、文档和低风险改进，进入计划队列。

### 15.2 故障报告

每个 P0/P1 故障必须记录：

- 发生时间和影响范围。
- 应用、配置、模型、数据版本。
- 复现条件和日志目录。
- 临时处置和是否回滚。
- 根因，而不是只写表面现象。
- 修复、测试和防止复发措施。

修复完成后将复现条件转换为自动测试或运维检查。

## 18. Definition of Done

任务只有满足以下条件才算完成：

- Issue 中的验收条件全部满足。
- 代码已进入 Git，提交可解释。
- 相关测试已新增或更新并通过。
- `DMX`、`DMX_test` 中受影响目标均验证。
- 无新增未解释警告和错误日志。
- 性能和算法指标已比较。
- 配置、日志字段和文档已同步。
- 数据或模型有明确版本及校验值。
- 有回滚方法。
- PR 已评审并合入 `main`。

“代码已经写完”“界面看起来正常”“测试过一次”都不等于完成。

## 19. 分阶段落地计划

- 按测试保护逐步拆分 `videothread.cpp` 和 `mainwindow.cpp`。
- 明确模块接口和负责人。
- 降低跨线程共享状态和隐式环境变量依赖。
- 建立长期性能趋势和技术债清单。

## 23. 日常节奏

建议采用一周一个小迭代：
